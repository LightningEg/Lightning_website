## Journey and operational checks

1. **Account:** one Supabase identity across website devices; setup/privacy controls remain separate from purchases. Sign-out clears private account/payment screens. Authentication return routes remain allowlisted. Email and OAuth provider delivery are external acceptance checks, not simulated as a real member login here.
2. **Quote and payment:** whole-EGP amount, 5 coins/EGP, minimum 10 EGP, bounded bonuses. Server snapshots exact coins, original amount, rate version, receiving details, email note and terms. A stale price cannot open a fresh checkout. The private QR requires that member's accepted pending checkout, uses a non-public runtime asset and sends no-store headers.
3. **Receipt:** PNG/JPEG/WebP, maximum 5 MB, reserved private path, owner-scoped uploads, bounded retries and evidence revisions. Receipt submission suppresses transfer instructions. Neither a screenshot nor a typed reference issues coins.
4. **Owner review:** AAL2 and active session, independent bank confirmation, original private receipt, customer details, exact matched bank total and a review note. Multiple partial incoming transfers fund one accepted quote. Approval, ledger credit and consumed references are one transaction; retries do not credit twice.
5. **Exceptions:** unmatched funds remain in the journal; under/overpayments require explicit member acceptance of a revised quote. Receipt review is invalidated after a change. Rejection/cancellation cannot hide received funds. Late-payment reopening and actual external returns resolve the terminal-state gaps. No control sends a bank transfer or creates an automatic refund.
6. **Marketplace:** expected-price confirmation, transactional wallet debit and permanent account inventory; repeat requests restore ownership rather than charging again. Unsupported native offers remain disabled. Website theme applicability is stated before purchase; main-site light/dark remains separate from For Geeks themes.
7. **Social rewards:** private draft → verification code/backlink in the member's own external post → URL/summary and rule consent → human review → optional coins/points. Source deduplication, post revisions and immutable ledger time enforce one reward and three coin-rewarded posts per rolling 30 days. Withdraw/edit/ban restoration cannot reset quotas. No forced disclosure line or automatic social posting is added.
8. **Deletion/retention:** unresolved paid requests and unreturned funds block deletion; cleanup uses Storage before account removal, scrubs sender identity and retains anonymized financial records. Pending evidence cannot be removed by the 90-day retention control. Deletion explicitly warns that online wallet and purchase inventory are removed.

### Remaining acceptance and release work

- **Real payment acceptance:** the owner must send/receive one genuine transfer, upload its original receipt, independently confirm actual bank funds, approve once, buy a website cosmetic and check inventory from another signed-in device. Local test transfers are simulations. Receipt authenticity and actual bank receipt remain human responsibilities.
- **Native PC/phone unlock:** app source includes part composition/offline signature verification, but no enabled production native bundles or deployed restore/redeem service were present. The claim/import screen, persistent verified entitlements, renderer, trusted public keys, private backend signing and supported-release acceptance must be completed before selling native items. Website ownership is not evidence of native delivery. This is the existing app milestone 8J, not a shipped feature of this audit.
- **Owner operations:** monitor the console and `hello@lightningeg.com`, publish processing availability through the editable checkout message, reconcile routinely and run receipt retention. There are no automatic bank-webhook credits or outbound approval emails. Email delivery/provider configuration and a physical authenticator enrollment are not tested with fake clients.
- **Auth provider setting:** Supabase reports leaked-password protection disabled. Enable it in the provider settings when available on the project plan; [Supabase guidance](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection). This cannot be established by application SQL tests.
- **Network evidence:** this execution environment blocks direct requests to the custom domain and Supabase changelog. Current relevant docs were consulted through the Supabase documentation connector. Public release publication is verified through GitHub Pages deployment status; browser behavior is tested locally. Do not describe this as a live browser/payment acceptance run.
