# Marketplace and account flow audit — 24 October 2026

Status: implementation reviewed and tested; production rollout explicitly authorized on 25 October 2026. Existing migration history was verified and baselined successfully. Deployment sequence and remaining launch requirements are listed below.

Scope: shared website/For Geeks identity, coins, InstaPay checkout, private receipts, owner operations, marketplace ownership, restoration, activation prerequisites, stories, privacy and deployment. The supplied design PDFs remain references, not executable policy. The account ledger is authoritative; Sheets may be a reconciliation export, not another writable balance.

## Deployment and verification

1. Baseline the twelve verified existing migration versions; retain a metadata backup before repair.
2. Apply migrations 1900 and 2000. They add quote/evidence APIs, upload reservations, lifecycle controls and MFA hardening. They do not enable payments, seed packages, issue coins or publish app assets.
3. Apply the follow-up migration 2200 to use the member-profile row, rather than auth.users, for the public views’ current-member guard. Deploy `delete-account`. Gateway JWT checking is disabled because the handler explicitly validates the bearer token with Supabase Auth, then uses that same user's RLS-scoped client. No service-role key is used by this endpoint. Origin, confirmation, body size and cleanup paths are checked.
4. Publish versioned website assets after local tests and GitHub checks pass.
5. Apply migration 2100 to retire the unquoted purchase and obsolete receipt-review endpoints. Old cached clients must reload.
6. Verify migration versions, grants/RLS, endpoint deployment, disabled payment state and wallet reconciliation. Inspect public deployed page/assets after the main merge.

The projected `profile_directory`/`profile_work` views intentionally run with owner permissions, expose a fixed allowlist of columns, and enforce consent/visibility in their definitions. Invoker permissions on the private base tables would break this public projection. The audit tightens membership checks so a deleted user's JWT is no longer treated as a current member. Supabase's definer-view/function advisories remain documented intentional API/projection findings; deny-all RLS on internal tables is intentional. Mutable function search paths are hardened. Leaked-password protection is a dashboard setting/plan capability and was not changed through unavailable configuration APIs.

## Before accepting real payments

- In the admin page: verify MFA, enter the actual InstaPay receiving address, recipient name and HTTPS QR image, create coin packages, then enable checkout. No destination or prices were invented.
- Perform one actual small transfer: email note, sender address/reference, receipt upload, owner bank reconciliation, approval, purchase and another browser sign-in. Confirm the same owned item appears without another charge. Exercise a rejection and a lost-response retry without sending another transfer.
- Confirm production email-confirmation, recovery and Google redirect URLs on both account pages. These checks require real account/email/provider interaction; isolated auth tests do not prove delivery.
- Publish support processing hours/contact and operate the receipt cleanup control. Review the final-purchase terms and error-correction route. Required legal rights remain preserved.

## Before enabling PC/phone delivery

Supply approved assets and compatible manifests; implement/accept the native claim/import UI, persistent verified entitlements and part renderer; install a trusted public-key registry in the released app; configure the private signing key only on the backend; deploy authenticated restoration and rate-limited one-time-code redemption; register only shipped item/platform/version combinations. Test first online redemption, replay/expiry rejection, lost-response recovery with a fresh code, another device under the same account, offline restart and unsupported app versions. Do not enable native listings before this acceptance. Portable signed licenses are copyable cosmetics, not strong DRM.
