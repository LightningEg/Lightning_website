    01 / mission

    One Clear Picture of Your Money

    Most people in Egypt keep money in a bank, a wallet, cash at home, a certificate, THNDR and gold. Most apps show one balance. Lightning puts all of it in one ledger, then answers where you stand, what is coming and why.

    Three things come first, in this order of effort: it must be efficient to use, insightful in what it says, and secure by default. Everything below is the proof.

    1.1The Test User

    Mohab is 31, salaried, lives in Cairo and counts in EGP. A full year of his money runs through the real screens as the acceptance test (tests/test_mohab_year.py). If a screen gets his year wrong, the build is not done.

    1.2Source-Available, Not Open Source

    We publish the code so developers can inspect the calculations and question our decisions. The licence is PolyForm Noncommercial 1.0.0: you may read, run and change it for non-commercial use. Commercial use needs written permission. Section 09 spells out the terms for contributors.

    02 / efficiency

    Thirty Minutes a Month

    The whole routine fits in half an hour, and each step is built to cost as few clicks as possible.

    2.1The Monthly Clock

    10 min
    upload your CSVs
    5
    adjust
    15 min
    sit down for analysis
    once a month= 30 min
    Download last month's CSV from each bank and wallet. Lightning only asks about what needs you: a new name, a possible duplicate, a row it can't place. One answer fills every row with that name. Between sit-downs, the Android beta catches spending as you go and bank SMS waits for your review.

    2.2Type Less

    Amount fields take sums, and date fields take shortcuts. Digits typed on an Arabic keyboard work too. Try it.

    A small reimplementation of the app's entry rules in lightning/core/money.py and the date parser, so you can feel them. The app is the reference.

    2.3Measured, Not Claimed

    Overview

    2.4Lean by Design

    1. 2.4.1

      No Frontend Build

      Server-rendered Jinja and vanilla JS. Nothing to compile, bundle or break.

    2. 2.4.2

      One Process, One File

      A single Python process and a single SQLite file. A backup is a copy.

    3. 2.4.3

      Rules Do the Repeating

      Tick "Use this category next time" and next month's statement sorts itself. A rule can be applied to the past, with one undo.

    4. 2.4.4

      Read One Section

      Contributors are not asked to read the whole architecture. The docs list which section a task needs.

    03 / insights

    Every Number Shows Its Working

    A figure you can't trace is a bug. Each one has one name, one formula and one function.

    The registry lives in lightning/core/figures.py. Screens read their labels and formulas from it, the glossary is generated from it, and tests check that every function it names exists.

    3.1Trace a Number

    Pick a figure and follow it down to the base figures. Select any row for its meaning. These are the registry's real formulas.

      Source: lightning/core/figures.py. Meanings are shortened from the registry.

      OverviewWhere do I stand, and what needs me?

      3.3Honest About Gaps

      1. 3.3.1

        Estimates Say So

        "If you sold today" is labelled an estimate. Zakat is an estimate by the common rule, for a scholar to confirm.

      2. 3.3.2

        Missing Is Never Zero

        A missing exchange rate makes a figure unavailable. A missing valuation gives no estimate and says why.

      3. 3.3.3

        Checks Never Go Green by Default

        Missing valuations make an integrity comparison incomplete, never green. The checks read only and never adjust entries.

      4. 3.3.4

        It Suggests, You Confirm

        An early payment, a raise or a rent change needs your explicit confirmation. Neither plan nor reserve changes silently.

      04 / security

      Locked by Default

      Your ledger is an encrypted file on your own computer. No account is needed, and the app serves only on 127.0.0.1.

      4.1Unlock Sequence

      One random data key opens the database. Two separate locks hold that key, so you can change a secret without re-encrypting anything. Run each path.

      password
      →
      Argon2id128 MiB · 4 passes
      →
      lock AAES-256-GCM
      →
      data key32 bytes · never typed↓SQLCipher database
      recovery key + answer
      →
      Argon2id256 MiB · 8 passes
      →
      lock BAES-256-GCM
      →
      Choose a path. Nothing here touches a real profile.
      An illustration of keys.json v2 as documented in the architecture. The password opens; the recovery key and answer together set a new password.

      4.2Defence in Depth

      1. 4.2.1

        Encrypted at Rest

        SQLCipher, keyed with a random 32-byte data key made once per profile. Backups use the same key.

      2. 4.2.2

        Three Secrets, Any Two Restore the Third

        A password of any length, a 12-digit recovery key shown once, and a security question. Lose the password and one other, and the data is gone. We say so up front.

      3. 4.2.3

        Slow Guesses

        Argon2id on both locks. Five free wrong tries, then waits of 1, 5, 15 minutes and 1 hour. Never a permanent lockout.

      4. 4.2.4

        Safe Changes

        A verified encrypted backup is written before any migration, and the migration aborts if that fails. The audit log is append-only. Deletes are recoverable.

      5. 4.2.5

        Optional Fingerprint on the Phone

        A third wrapping of the same key under an Android Keystore key that needs a strong biometric. The password and recovery key always still work.

      What It Does Not Protect

      Nothing protects an unlocked PC from malware. Freed memory is not wiped: decrypted fragments may persist in freed memory, crash dumps, the page file or the hibernation file. Wiping made encrypted reads about three times slower, so the owner chose speed. A copied database without its key file is a 256-bit problem; with the key file, an attacker can guess offline, and Argon2 slows each guess.

      Found a flaw? Write to geeks@lightningeg.com.

      05 / principles

      Eight Rules the Code Holds

      These are decisions, not wishes. Each one is checked by a test, a contract or a migration rule.

      1. 5.1

        One Ledger

        Real money is only what the ledger says. Registers, budget actuals, investments and reports are views of it.

        TransactionService, the only writer of postings
      2. 5.2

        Plans Move No Money

        A budget, reserve, scheduled bill or forecast never appears in a ledger figure. A plan figure is always labelled as one.

        the three-layer split, section 06
      3. 5.3

        One Figure, One Name, One Function

        Every figure has one name and one formula. Screens call the function the registry names; routes never compute.

        lightning/core/figures.py, tests/test_figures.py
      4. 5.4

        Plain Code Does the Maths

        Calculations, matching, prices and categories are ordinary code, never AI calls. You can read them and re-run them.

        AGENTS.md product rules, and the services themselves
      5. 5.5

        Decimal, Never Float

        Money is Decimal in Python and scaled integers (_e6) in SQLite. No binary floats in financial logic.

        the persistence contract
      6. 5.6

        Local Only

        Your data stays on your computer and never enters Git. The server listens on 127.0.0.1.

        encrypted profiles, section 04
      7. 5.7

        Names Stay Canonical

        Similar spellings are suggestions you pick. Nothing is silently merged and no counterparty is created behind your back.

        the search and identity contract
      8. 5.8

        Wrong Is Worse Than Slow

        A silent wrong result costs more than an extra click. Missing prices stay pending; cost is never quietly used as a quote.

        the reevaluation ledger

      06 / architecture

      Ledger, Plan, Report

      Lightning is a local-first, single-user modular monolith: one Python process, one SQLite database, a server-rendered browser UI. Correctness first, then clear ownership of data, then new asset types without duplicated transaction logic.

      6.1Three Layers

      These describe what data is, not which package may import which. Pick a layer.

      Accounts, posted transactions and ledger lines, prices and valuations, and money held for others.

      accountstransactionsassetsinvestmentsmoney_from_othersphysical_items

      moves money: yes. Only TransactionService writes postings.

      Budget rules and carryover, reserves, planned items and payments, sale factors and the cash forecast.

      budgetingreservesplanning

      moves money: no. "Record and mark paid" posts an ordinary transaction through TransactionService, then the plan links to it.

      Nothing of its own. Figures are computed on read from the ledger and the plan, and each screen says which.

      reportingPositionServiceinvestments.reportintegrityui

      moves money: no. Integrity checks never adjust entries.

      6.2Dependency Direction

      Dependencies point down. import-linter checks the contracts on every test run, and bootstrap.py is the composition root. Cross-module work calls public services, never another module's repository.

      ui/FastAPI routes, Jinja templates, small vanilla JS. No SQL, no calculations.
      workflows/transactional use-cases that span modules
      planning/recurring items, loans, what you owe, cash forecast (read-only)
      domain services/accounts, assets, categories, transactions, investments, deposits, budgeting
      reporting/read-only queries and derived views
      database/SQLite, migrations, seed, backup, settings, audit
      core/dates, money, identifiers, posting rules. No app dependencies.

        7.2The Real Check

        This is the function that enforces it, trimmed to the lines that matter. It is pure Python with no database, so the rule is easy to test.

        lightning/core/ledger.pyopen the file ↗
        def validate_posting(lines: list[PostingLine]) -> None:
    """Raise ValidationError unless the lines form a valid posting."""
    # ...
    for i, line in enumerate(lines, start=1):
        # ...
        if line.effect in (Effect.INFLOW, Effect.OUTFLOW) and line.category_id is None:
            raise ValidationError(f"Line {i}: money in and money out need a category.", "category")
        # ...
        if line.effect == Effect.INTERNAL:
            internal_total += line.amount_base
    if internal_total != ZERO:
        raise ValidationError(
            f"Internal movements must net to zero (they net to {internal_total})."
        )

        7.3Precision and Migrations

        Money, prices and quantities are Decimal or integer _e6. Dates are ISO yyyy-mm-dd. Migrations are ordered and append-only: never edit an applied migration. Persistent state needs a new migration and a module that owns its table. Foreign currency stores the native amount, the dated base amount and the rate used, and stored values are never rewritten when rates change.

        08 / run it

        Clone, Test, Open

        You need Python 3.11+ and Git. The sample household runs in its own database, so your own data is never touched.

        # get the code and prove it works
$ git clone https://github.com/elfekimuhammed/Lightning.git
$ cd Lightning
$ pip install -r requirements-dev.txt
$ python -m pytest
$ lint-imports
        # Mohab's household, rebuilt on every start → http://127.0.0.1:8766
$ python -m lightning --demo
        # the encrypted-profile UI in a browser (Linux)
$ python -m lightning --profiles

        On Windows, run.bat sets everything up on first run. Options: --db, --port, --no-browser.

        Beta, so Use Dummy Data

        This is v1.1.0-beta.1. Ordinary-PC acceptance, legacy import and in-app backup restore are not finished. Test with sample data and keep an independent backup of anything real.

        09 / contribute

        How to Send a Change

        1. Read what your task touchesStart with the project overview, then one section of the architecture. The docs list when to read each section.
        2. Open an issue firstSay what you want to change and why. Questions for the owner live in issues too.
        3. Branch as yourname/featureOne feature per branch, with a clear name. Never a random suffix.
        4. Define it, then build itA new concept goes in the glossary first. New persistent state needs a migration and a module that owns its table.
        5. Test itRun pytest and lint-imports. For UI changes, check populated and empty data at a 390px viewport.
        6. Log itAdd a changelog entry of three lines or fewer under Unreleased, then open the pull request.
