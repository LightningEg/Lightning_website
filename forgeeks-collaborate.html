Eight steps from an idea
to merged on main.

The same path for a stranger, a teammate and an AI: issue, fork, pull request, checks, review, squash. Nobody pushes to main, and every gate is enforced by GitHub, not by trust.

Pick an issue $ read the flow
01 / flow

From issue to merge.

Eight steps, nothing to install. Steps 1 to 4 are yours; 5 to 8 are shared with the maintainers.

01

Pick an issue

Open the good first issues with no assignee. Each says what is wrong, when it is done and which file to open.

02

Comment /take

A bot assigns it to you and adds the taken label. One at a time; /drop gives it back; 14 quiet days free it.

03

Fork and branch

Branch in your fork, named who/feature: yourname/fix-gold-label. One feature per branch.

04

Build and test

Codespaces needs nothing installed. Locally: python -m lightning --demo, then python -m pytest -q.

05

Open the pull request

Write Closes #123 and one line on how you checked it. Tick the box: no real data, passwords or keys.

06

Checks run

tests, dependency-review and analyze must be green. A first-time fork waits for the owner to approve the run.

07

Review

A code owner who is not the author approves the exact latest diff. A new push dismisses the approval. Every conversation gets resolved.

08

Squash and merge

One squash commit on main. The branch goes, the issue closes, and maintainers add the changelog and brand details.

$ git clone https://github.com/<you>/Lightning.git && git switch -c you/your-feature && python -m pytest -q
02 / who

Who can do what.

Merge rights are small on purpose: the owner and the AI bot accounts. Everyone else works from a fork.

peoplehow they work

  • [owner]

    OwnerAdmin, the only one. Reviews and merges everything, including every outside pull request.

  • [team]

    Internal teamTrusted humans with Triage. Fork, branch, open PRs, label and assign. They cannot push or merge.

  • [open]

    Open contributorsAnyone. Fork, branch, open a PR from the fork. No access to the repository itself, until the owner decides.

ai teammatesclaude, codex, luna

  • [write]

    Own bot account eachWrite access through one team, never the owner login. They push their own branch and open a PR.

  • [merge]

    May merge, under rulesOnly when every gate below holds and a different identity approved. Never their own work alone.

  • [never]

    NeverPush to main, approve an outsider’s PR, or touch an owner-only path without the owner.

03 / gates

What a change must pass.

These rules are in the repository’s ruleset and apply to AIs too. Only the owner can bypass, and only through a pull request.

on every pull requestenforced by GitHub

  • [pr]

    Pull request onlyNobody pushes to main. No force-push, no deletion, linear history.

  • [ci]

    Three green checkstests, dependency-review and analyze (CodeQL), up to date with main.

  • [owner]

    One code-owner approvalFrom the owner or a different AI account. GitHub blocks self-approval.

  • [fresh]

    Approval after the last pushPush again and the approval is gone. Review is of the exact final diff.

  • [talk]

    Conversations resolvedEvery review thread closed before the Merge button works.

owner onlythese paths need the owner

  • [path]

    Workflows, rules and templatesThey run on machines, so the owner reads them.

  • [path]

    packaging/, android/, cloudflare/What ships to people’s devices.

  • [path]

    Scripts, and tests/conftest.pyCode that runs with a developer’s permissions.

  • [path]

    AGENTS.md, CLAUDE.md, LICENSE, SECURITY.mdThe rules and the legal text.

  • [path]

    v* release tagsOnly Admin creates them, and a release job waits for the owner’s click.

04 / rules

Ground rules.

Short, and the same for everyone.

01

Dummy data only

Never put real financial data, passwords, keys or screenshots of real money in a commit or issue. The demo household is fictional.

02

Security is private

A vulnerability goes to the private advisory form, never a public issue. Revoke a leaked secret first, then clean up.

03

Money lives in Python

Financial calculations stay in services, never templates or JavaScript. Say how a change can fail and show the test.

04

Brand and tests

Visible changes follow the guideline. Run the tests of what you changed; CI runs the full suite.

05 / ai

If you are an AI.

Claude, Codex and Luna cannot talk to each other, so the repo carries everything. Same pull request path, plus a hand-off.

01

Start from the repo

The repository is the only channel. Read NOW.md and the last 15 commits, then branch from a fresh main.

02

Claim long work

Work longer than one sitting goes in the Claimed table first, so two AIs never edit the same files.

03

Small finished steps

Test, commit and push each step. Findings become one file each in report/; fixing one deletes it.

04

Hand off

Changelog entry, update the files you touched, drop your claim, add next steps with a Read: line, then open the PR.
